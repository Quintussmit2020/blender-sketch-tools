# Sketch Tools - agreed corrections to SKETCH_TOOLS_PLAN.md

Agreed with the project owner on 2026-10-22 after a review of the plan. Where this file and the plan disagree, this file wins. Everything else in the plan stands. Do not silently change the data model or the mitre approach.

## Target

- Development and test Blender: 5.1.1 at `C:\Program Files\Blender Foundation\Blender 5.1\blender.exe`. Minimum supported stays 4.2.0 (`blender_version_min = "4.2.0"`).
- Avoid APIs removed or changed between 4.2 and 5.1. In particular: do not read or write `bpy.props`-defined properties through ID-property dict access (`obj["sketch_tools"]`); always go through the RNA attribute. Use `gpu` (never `bgl`). Builtin shader names without the `3D_` prefix.

## C1 - Extrude caps (replaces plan 5.3)

Tested live in Blender 5.1.1: `bmesh.ops.join_triangles` only ever produces quads, never ngons. `mathutils.geometry.tessellate_polygon` also returns triangles with inconsistent winding.

- Cap with no holes: one ngon built directly from the loop's vertices. No tessellation.
- Cap with holes: `tessellate_polygon([outer, hole1, ...])`, create the triangles on the shared cap vertices, make the cap's winding consistent (recalc normals on just those faces or orient each triangle by its signed area), then `bmesh.ops.dissolve_limit(angle_limit ~1e-3, edges=<interior cap edges only>)`. Tested result: a 12-gon with a square hole becomes two 10-gons joined by bridge edges. That is the accepted result.
- Never use `join_triangles` for caps.

## C2 - Mitre limit keeps the sign of u (Phase 2, sweep)

The clamped vertex is `P_i + b_hat * sign(u) * (sw_mitre_limit * |u|)` where `b_hat = normalize(n_(i-1) + n_i)` is the bisector of the two left normals. The plan's unsigned form pushes right-side (negative u) points to the wrong side.

## C3 - Shared vertices instead of welding (replaces plan 5.4)

Build cap faces on the same `BMVert`s as the side walls. Do not run `remove_doubles` over the extrude output; it would merge separate loops that touch at a point and break the manifold result.

## C4 - Custom profile dependency (Phase 2)

Keep a reverse lookup so that when a sketch used as `sw_custom_object` by other sketches is rebuilt or edited, every sketch that uses it is rebuilt too. Guard against cycles (a sketch using itself, or A uses B uses A).

## C5 - Smooth sweep corners (Phase 2)

When `sw_smooth` is on, also mark a station's ring edges sharp where the path turns more than 30 degrees at that station. Fillet arcs turn by small steps, so they stay smooth.

## C6 - Undo (extends plan 7)

Register an `undo_post` (and `redo_post`) handler that rebuilds every sketch object, alongside the `load_post` pass. Handlers must be `@persistent` and removed on unregister.

## C7 - Apply naming (replaces part of plan 7 Apply)

On Apply, if the sketch is kept, first rename the sketch to `<name>.sketch`, then give the applied mesh the original sketch name. If the sketch is deleted, the mesh simply takes the freed name.

## C8 - Junction loops (extends plan 4 step 3)

A chain that starts at a junction J and returns to J without passing any other junction is closed (if it has at least 3 distinct points). Example: a rectangle with a line hanging off one corner extrudes as the rectangle, and the hanging line is an open chain.

## C9 - Weld across chains before walking (extends plan 4 steps 1 and 5)

In the resolver's temporary bmesh, weld coincident vertices (distance 1e-5) across the whole sketch before walking chains, so two loose endpoints at the same spot form a closed loop. Never write this weld back to the sketch mesh. When welded vertices have different fillet radii, keep the larger.

## C10 - New vertices start sharp (Phase 1)

Blender copies point attributes to new vertices (Ctrl+RMB extrude, duplicate), so a new vertex next to a filleted corner would inherit its radius.

- Add a second POINT attribute `st_fillet_id` (INT). Whenever the add-on writes a non-zero radius to a vertex, it also writes a fresh random non-zero 31-bit id to that vertex.
- Cleanup pass, run at the start of `rebuild` while the sketch is not in edit mode: among vertices with a non-zero radius, any vertex whose id is 0 or is shared with a lower-index vertex gets radius 0 and id 0. Blender appends new vertices at the end, so the original keeps its radius.
- Write the attributes back only if something actually changed, so the depsgraph handler cannot loop.

## C11 - Nesting robustness and crossing loops (extends plan 4 step 7)

- To test whether loop A is inside loop B, use the first point of A that is not on B's boundary (distance > 1e-6). If every point of A is on B's boundary, the loops are treated as not nested.
- If any segment of A properly intersects any segment of B, add a warning naming both loops ("Loops 2 and 5 cross; extrude result may be wrong").

## C12 - Mitre limit wording (fixes plan 3.1)

`sw_mitre_limit` is a multiple of each profile point's own |u| (plan 6.2), which makes it a pure corner-angle threshold. The "multiple of profile half-width" wording in 3.1 is wrong.

## Phase 1 scope notes

- `sketch.new` with plane FACE, and `sketch.set_plane_from_face`, are launched from a panel button, so the mouse is not over the viewport. They enter a short modal: the header says "Click a face", LMB in a 3D viewport picks the face via `scene.ray_cast`, Esc/RMB cancels.
- `sketch.new` enters edit mode in vertex select mode and activates the Phase 3 Sketch tool (`sketch_tools.sketch`, `ui/tool.py`) in the invoking 3D view. This replaces the Phase 1 stand-in (Blender's built-in Extrude to Cursor tool). The switch happens only after edit mode is entered, is skipped silently when there is no 3D view, and a failure to switch (including a CANCELLED result) never fails sketch creation; it is printed once.
- The headless tests run with `blender.exe --background --factory-startup --python sketch_tools/tests/run.py` and must exit non-zero on any failure.

## C13 - Sweep normals by construction (Phase 2, replaces the recalc in plan 6.2)

Phase 1 QA showed `bmesh.ops.recalc_face_normals` flips disconnected or open shells (hole walls with caps off). The sweep builder must orient every face correctly by construction, from the profile ring winding and the travel direction, and must not call `recalc_face_normals`. Closed profile rings are CCW in (u, v) for solids and CW for holes (TUBE inner ring, odd-depth custom loops). Normals point out of the swept solid for closed paths, open paths with caps, and open paths without caps.

## C14 - Phase 2 module contract (agreed 2026-10-22)

- `core/profiles.py`: `ProfileRing(points: list[(u, v)], closed: bool, depth: int, parent: int | None)`; `library_profile(kind, width, height, radius, thickness, segments) -> (rings, warnings)`; `profile_from_chains(chains) -> (rings, warnings)` (from `ResolvedSketch.chains`, local x to u, local y to v); `profile_from_splines(splines) -> (rings, warnings)` where each spline is plain data `{"type": "POLY"|"BEZIER"|"NURBS", "points": [...], "cyclic": bool, "resolution": int}` (POLY and NURBS points are (x, y, z) tuples; BEZIER points are `(co, handle_left, handle_right)` triples); `transform_profile(rings, pivot, offset_u, offset_v, rotation_deg, mirror_u) -> rings`.

## C15 - Sketch draw tool behaviour (Phase 3, agreed 2026-10-22)

- One `sketch.draw` run draws one chain, rectangle or circle and is one undo step (`bl_options = {'UNDO'}`). A cancelled run leaves no step and no geometry. The first click is not written to the mesh until a second point exists.
- Ending: RMB, N, and Enter with nothing typed all end the chain and keep it (a lone point, or a rectangle or circle without its second point, is cancelled instead). Enter with a typed value commits that point and the chain continues. N is therefore the same as RMB: the next click starts a new, unconnected chain because each run is one chain.
- Angle lock (Shift) snaps the segment direction to the nearest multiple of 45 degrees from the previous segment (first segment: from sketch X), length kept. Typed angle is the turn from the previous segment in degrees, counter-clockwise positive.
- Snapping (Ctrl held with Blender's snap magnet off; the magnet inverts this, see C23) snaps to the nearest sketch vertex (session vertices included) within `snap_pixel_threshold` pixels and reuses it, else (C22) to a visible vertex, edge midpoint or edge point of another mesh object, else to the grid. Snapping onto the chain's first vertex closes and ends the chain.
- Units (revised after QA round 2): the `grid_increment` preference has `subtype='DISTANCE'`, so Blender stores it in local units and does the display scaling itself. The stored value is the grid step in sketch local units, used directly with no division. Typed lengths are in the scene's base unit with the unit scale applied (metres for Metric; `length_unit` such as cm is not applied): a typed length L is `L / effective_scale` local units, and the overlay readout shows local lengths multiplied by `effective_scale`, where `effective_scale = scene.unit_settings.scale_length` unless the unit system is None, in which case it is 1.0 (Blender ignores `scale_length` then). The conversion happens where `DrawSession` is built (`unit_scale=`, via `draw_logic.effective_unit_scale`). Typed lengths are plain floats, no unit parsing. Object scale is not accounted for: sketches are created at unit scale.
- Pointer events outside the modal region's bounds, or over the area's HEADER, TOOL_HEADER, TOOLS, UI, HUD, ASSET_SHELF or ASSET_SHELF_HEADER regions (which sit inside the WINDOW region's rectangle with region overlap; compared in window coordinates, width and height > 1), never add points. While a run is live a second `sketch.draw` invoke returns PASS_THROUGH without starting and without a report (see C16). The run ends when the 3D view is lost, see C16. Presses (and their releases) outside pass through so the header, toolbar and sidebar stay usable; the overlay draws only in the region the run started in. Non-keyboard, non-mouse events (timers, window focus) always pass through. The first click may carry Shift and Ctrl (the LMB keymap item accepts any of them, Alt stays excluded for navigation); R and O stay modifier-free.
- Keys: R (rectangle), O (circle), P (polyline) switch mode while no second point exists; the tool keymap also starts `sketch.draw` in rectangle or circle mode on R and O, waiting for the first click. Phase 8 (C21) adds A (arcs) inside a run and the header shape enum; the LMB item then starts the header's shape. Numpad digits navigate the view until a number is being typed, then they type.
- Overlay exclusion also applies to the press that would start a run (QA round 3): `invoke` runs the projector's `contains` check for the starting LEFTMOUSE before creating the editor or controller and returns PASS_THROUGH when it fails. R and O starts wait for a click that goes through the normal handler, so the same check applies there.
- Navigation gizmo (QA round 3, an approximation): the axis ball and zoom, pan, camera and ortho buttons live inside the WINDOW region and Python cannot ask which gizmo is hovered. While `space.show_gizmo` and `space.show_gizmo_navigate` are on, `navigation_gizmo_rect` adds a window-space rectangle to the projector's overlays, anchored to the top-right corner of the region's visible area (below top-aligned HEADER and TOOL_HEADER regions, left of a right-aligned open UI region). Size, in units of the UI scale factor (`preferences.system.ui_scale`, which includes OS scaling; `dpi / 72` where it reads zero): `0.99 * gizmo_size_navigate_v3d + 11` wide and tall, or `1.1 * gizmo_size_navigate_v3d + 128` tall when `preferences.view.show_navigate_ui` (the zoom/pan/camera/ortho buttons) is on, plus a 4 px margin on the open sides. The constants were measured on 5.1 by diffing screenshots with the gizmo on and off, at gizmo sizes 80 and 120 only; the ball slope was then raised from 0.97 to 0.99 (QA round 4) so that sizes 30, 50, 80, 120 and 200 were all checked as covered. The rectangle is a little larger than the drawn gizmo, so a point cannot be placed in that corner of the viewport during a run; presses there (and their releases) pass through like overlay presses.
- Pass-through is per button: an RMB press outside the region passes through with its release, and the release, CLICK and CLICK_DRAG events of any passed LMB or RMB press pass through too. The record of the passed press lasts until the next press of that button, because CLICK may arrive before or after the release.
- Quad view (QA round 4, known limitation, no code change): each quad's navigation gizmo is drawn much smaller than the rectangle computed from the preferences, so each quad loses more corner area than needed during a run.
- A passed Alt+LMB press (navigation) is recorded like any other passed press, so its release, CLICK and CLICK_DRAG pass through even when Alt is released first.

## C16 - Trim and Extend behaviour (Phase 4 part B, 2026-10-23)

- Both are modal operators started from the Sketch panel buttons (or any 3D view region). A panel button runs in the sidebar region, whose pointer coordinates are relative to the sidebar, so `invoke` there re-invokes the operator under `temp_override(region=<the area's WINDOW region>)` and returns CANCELLED itself (no undo step). Neither operator takes the starting click: they wait for the first LMB.
- Undo: one run is one undo step, as in C15, because Blender cannot undo a modal operator's edits piecemeal. RMB and Enter keep every edit and finish (`bl_options = {'UNDO'}`); a run that changed nothing returns CANCELLED, so no empty step. Esc cancels the whole run: the first edit copies the whole edit mesh into a temporary Mesh datablock (`update_from_editmode` + `Mesh.copy()`, which keeps attributes of every domain, edge attributes such as crease and bevel weight, seams, vertex groups, shape keys, hide and select flags, select history and element order), and Esc, an error and add-on unregister put it back with `bm.clear()` + `bm.from_mesh()` (the bmesh's `select_mode` is read before the clear and set again after, because `clear()` zeroes it). The copy carries a fake user so an Outliner purge during the run cannot delete it; `release()` removes it explicitly. A file save during a run must not write it: `save_pre` clears the fake user of the live snapshots, so a zero-user mesh is not written, and `save_post` (and `save_post_fail`, so a failed write cannot leave it unpinned) sets it again. Any save path that skips the save handlers (autosave, `quit.blend`, Save Startup File) and a memfile undo step can still carry a snapshot; this was not forced in a test, so the guarantee is the cleanup, not the pinning: the copy is tagged with the custom property `sketch_tools_snapshot` (it survives memfile undo, save and `quit.blend`), and `load_post`, `undo_post` and `redo_post` remove meshes that carry the tag, are named `sketch_trim_backup` or `sketch_trim_backup.NNN` and are held by nothing but a fake user, and do nothing while any sketch modal is live. A user's own mesh with that name and a fake user has no tag and is never touched. `save_post_fail` is hooked only where Blender has it (the manifest minimum 4.2 may not). Both only touch those meshes (and their shape key datablocks), never an object or a rebuild. Every exit path (finish, Esc, error, cancel, edit mode left, `close_all`) removes the temporary mesh and its copied shape key datablock, so no orphans are left. Tab is swallowed during a run; edit mode is left through the header mode menu. Leaving edit mode during a run does not restore: the edits made so far stay, the snapshot is dropped, and the modal ends on the next event with CANCELLED. Losing the 3D view (the area is retyped or closed, so there is no projector) ends a Trim or Extend run the same way on the next event, but through the normal finish: the edits stay and the result is FINISHED, or CANCELLED when nothing was edited. The draw tool ends on the same condition like it does for leaving edit mode: uncommitted work is dropped and the result is CANCELLED. Fillet already aborted without writing. Edit > Undo during a run cancels the modal and its pending edits and also steps back the step before the run, because the run is not an undo step yet. Panel operators used during a run (Height, Fillet Radius field, Apply and so on) edit the mesh under the snapshot, so a later Esc reverts them too. A running Trim, Extend, Fillet or Sketch draw run refuses a second start of any of the four (`modal_common.any_sketch_modal_live()`); Trim, Extend and Fillet report the warning "Finish the running sketch tool first" and return CANCELLED, which is what lets Blender show it. Draw refuses silently and returns PASS_THROUGH: its tool keymap re-enters on clicks in a second viewport or a gap of the sidebar, those must reach whatever is under the pointer, and Blender discards the reports of an invoke that passes through anyway (verified with a control operator; Phase 4 QA round 3). A Fillet commit whose corner vertices were deleted by a panel operator during the run writes nothing, reports a warning and cancels.
- Trim: LMB picks the visible edge nearest the cursor within `snap_pixel_threshold` px. The clicked parameter is the cursor ray's hit on the sketch plane projected onto the edge (the screen parameter only when the ray misses the plane). Crossings with every other visible edge are computed in 2D; a contact that is only a shared end vertex, parallel and collinear edges, and the edge's own end touching another edge are not bounds. Crossings within 1e-5 of each other or of an end of the edge are one point or the end. The interval between the bounds around the click is removed: the edge is split at the interval's interior bounds with `bmesh.utils.edge_split`, the crossing edges are split at the same points (a crossing that lands on an existing vertex of that edge reuses the vertex), the sub-edge is deleted, and an original end vertex left with no edges is deleted. Only crossings at the removed interval's bounds split anything; other crossings of the edge stay as they were.
- Weld: per bound, the new split vertices (the trimmed edge's and each crossing edge's) are merged with `bmesh.ops.weld_verts(targetmap=...)` into one target vertex. The target is an existing vertex when the group has one, so it keeps its position, fillet radius and id deterministically (`remove_doubles` picks by coordinate order, not list order, and could keep the new vertex instead). The group's existing vertices are the crossings that land on a vertex of the crossing edge, plus any other existing vertex within 1e-5 of the bound's point (for example the end of an edge collinear with the trimmed one, which is not a crossing because parallel edges are skipped). A group made only of new vertices welds to its first one. Nothing else in the mesh is welded.
- New vertices from `edge_split` get `st_fillet_radius` 0 and `st_fillet_id` 0 explicitly (Blender interpolates the end vertices' attributes onto them, see C10 and plan 8.8). Existing radii and ids are never written.
- Extend: LMB picks the nearest visible vertex within `snap_pixel_threshold` px that has exactly one edge (`len(link_edges) == 1`, hidden edges included, matching the resolver) and whose edge is visible. The 2D ray runs from it along its edge direction (away from the neighbour). The nearest edge hit with distance above 1e-5 wins (the vertex's own edge, parallel edges and edges behind are ignored). A hit within 1e-5 of an edge's end vertex joins that vertex; otherwise the edge is split there with a sharp vertex. Then one edge from the loose end to that vertex is added. No hit: the mesh is not touched and a WARNING "Extend: no edge in that direction" is reported.
- Overlay: the existing `DrawOverlay` with a `Preview`. Trim draws the interval that would go as the yellow band, the whole edge as the cyan guide and the bounds as markers; Extend draws the extension strip, the hit marker and the loose end as the green square, with "No edge ahead" at the cursor when nothing is hit. Pointer pass-through (region bounds, header, toolbar, sidebar, navigation gizmo, Alt+LMB, per-button release and click records) is exactly C15's. Keyboard is swallowed except Esc and Enter; numpad navigation and all mouse navigation pass through.
- Quad view: Trim and Extend, like the draw tool, do not handle quad view specially; the C15 known limitation applies unchanged (the navigation gizmo rectangle is the single-view estimate, so each quad loses more corner area than needed). Fillet refuses to start in quad view.
- Area lifetime (QA round 5): a closed Area does not raise ReferenceError, its struct dangles. The modals therefore keep `area.as_pointer()` and look the area up live (`modal_common.find_area`, across all windows' screens) for the header text, the redraw and Fillet's view; the WINDOW region is found by iterating `area.regions`. A missing area, a type other than VIEW_3D, a missing WINDOW region or a missing active space means no view: Fillet aborts and Trim/Extend finish through their normal paths, and header and redraw calls are skipped silently. `navigation_gizmo_rect` returns None for an area without an active space.

## C17 - Subdivide sketch edges (Phase 6, 2026-10-23, extends plan 8.8)

- Module split: `core/subdivide_logic.py` (pure: counts and split points from plain floats), `ops/subdivide.py` (the operator, edit-bmesh work), `ui/menus.py` (the two menu entries). The panel button is in `ui/panel.py`.
- Edge set: visible edges only (an edge with a hidden edge flag or a hidden vertex is never touched). In vertex select mode an edge counts when both its vertices are selected, so raw vertex flags without an edge flush still work. In edge and face select mode the edge's own flag decides, because two opposite sides of a square select all four vertices without selecting the other two sides. A lone selected vertex implies no edge.
- Geometry in sketch local 2D: length and split points use x and y only, new vertices are written at z = 0 (an off-plane end vertex is treated as on the plane, as the resolver does). Zero-length means 1e-6 or less. COUNT gives `cuts` new vertices per edge; LENGTH gives `ceil(length / max_length - 1e-6) - 1` (the slack keeps an edge of exactly twice `max_length` at two parts despite float noise) and leaves edges already short enough alone.
- LENGTH mode is bounded at 1000 parts per edge (999 new vertices), because dragging `max_length` down in the redo panel on a long edge would otherwise build millions of vertices. A clamped edge is reported with a WARNING ("N edges limited to 1000 parts") and the result is still FINISHED.
- `max_length` is a DISTANCE property (default 0.5, minimum 0.001) stored in sketch local units, like `grid_increment` in C15; Blender does the display scaling. Object scale is not accounted for.
- Cutting uses `bmesh.utils.edge_split`, repeatedly from the first vertex, so the original edge keeps its identity as the last piece, edge data (crease, seams, bevel weight) is interpolated by Blender, existing vertices and their radius and id are never written, and chains, closed loops and junctions keep their topology. Positions come from the pure helper, not from the split fraction. Every new vertex gets `st_fillet_radius` 0 and `st_fillet_id` 0 explicitly (C10), overwriting what the split interpolated.
- Selection: afterwards only the new vertices are selected (and any edge with both ends new, a normal flush); faces, the select history and everything else are deselected. Selection by vertex needs vertex select mode, so a run started in edge or face mode switches `tool_settings.mesh_select_mode` to vertex mode after planning and before cutting. This is the one side effect on tool settings.
- The operator does nothing and returns CANCELLED (so no empty undo step) with a WARNING when no edge qualifies: "Select the sketch edges to subdivide" (no selected visible edge), "The selected edges have no length" (COUNT) or "No selected edge is long enough to subdivide" (LENGTH). No change is made before this check.
- Phase 4 guard: `execute` refuses with `modal_common.BUSY_MESSAGE` and CANCELLED while `any_sketch_modal_live()`. `poll` does not check it (a failing poll would grey the button with no explanation). Poll is edit mode plus an active sketch, with no requirement for a 3D view area, since the operator never reads the view.
- Undo is Blender's own for a REGISTER + UNDO operator: one step. Operators called from Python do not push undo steps unless asked (`bpy.ops.sketch.subdivide('EXEC_DEFAULT', True, ...)`); the tests do that and, in a GUI run, a simulated click on the panel button followed by Ctrl+Z restored the exact mesh and selection, and Ctrl+Shift+Z redid it.
- Menus: `sketch.subdivide` is appended (after a separator) to `VIEW3D_MT_edit_mesh_edges` and `VIEW3D_MT_edit_mesh_context_menu`, drawn only when the active object is a sketch (checked in the draw function on every draw). The context menu picks its content by select mode, but an appended function draws in every mode, so the entry also shows in vertex mode, where sketches are edited; the plan's "edge context menu" is a subset of that. Blender's own Subdivide stays in those menus unchanged. Unregistering removes both draw functions; the entry's label is "Subdivide Sketch Edges" to tell it from Blender's.
- The Sketch panel has a plain "Subdivide" button (edit mode, active sketch) after Fillet, Trim and Extend. It runs with the last used `mode`, `cuts` and `max_length`, which are changed in the redo panel; plan 9's "with cuts" is therefore the redo panel, not a field in the N-panel. The redo panel draws the mode and only the relevant one of `cuts` and `max_length`.

## C18 - Fillet exact-fit tolerance (2026-10-23, extends plan 4.1)

- A fillet whose tangent distance equals the clamp limit (0.5 x the shorter adjacent segment) must not be reported as clamped, though float32 vertex coordinates and the float32 radius attribute put it a hair over. `core/geometry2d.fillet_corner` reports a clamp only when `t - limit > 3e-7 * max(limit, largest absolute coordinate of the three points)` (`FILLET_FIT_TOLERANCE`). Relative to the coordinates, not only to the segment, because the stored coordinates are rounded to about 6e-8 of their magnitude. Inside the tolerance the tangent distance is still set to the limit (the arc is unchanged to within the float error).
- The whole computation runs in Python floats (unit vectors in float64, theta = `atan2(|cross|, dot)`). The first version used float32 `Vector` maths with `acos`, which amplifies float32 error near 0 and pi and read exact fits at about 1-20 and 160-179.4 degrees as clamped (2556/4000 samples at 1-5 degrees, 502/4000 at 175-179.4). The skip rules (under 1 degree, over 179.5 degrees) are unchanged, just computed in float64.
- Measured, for a fit exact for the stored (float32) geometry, radius rounded to float32, angles 1 to 179.4 degrees, 7 rotations, leg pairs 1/3, 3/1, 1/1, 0.01/0.02, 100/300, offsets 0 to 1e5: worst `(t - limit) / limit` is 5.96e-8 at every offset (the float32 rounding of the radius, 2^-24, so it is a hard bound) and worst `(t - limit) / scale` is 3.6e-8 (offset 0), 2.9e-8 (1), 1.1e-8 (10), 1.7e-8 (100), 2.7e-9 (1e3), 2.9e-10 (1e4), 2.8e-11 (1e5). Corners the analytic geometry defines (radius from the ideal angle, vertices then rounded to float32) add the vertex rounding amplified by 1/sin(theta): worst `(t - limit) / scale` over offsets 0 to 1e5 is 5.4e-8 for 30-150 degrees, 6.3e-8 for 20-160, 2.0e-7 for 5-175 and 1.3e-6 for 1-179.4. 3e-7 is 5x the hard bound and 1.5x the 5-175 degree figure.
- Guarantee: a fit that is exact for the stored geometry never warns at any angle that is not skipped, at any coordinate magnitude tested (to 1e5). An overshoot warns whenever it exceeds `3e-7 * max|coordinate| / limit` of the limit: with a short leg of 1 (limit 0.5) the first warned overshoot measured is 0.010 percent at offset 0, 0.070 at 1e3, 0.61 at 1e4 and 6.0 at 1e5. So 0.1 percent over always warns up to coordinates of about 1e3 and 1 percent over up to about 1.6e4. Not covered: at 1e4 and more the warning cannot see overshoots under that bound (the clamped geometry is still correct), and a near-flat corner (over 175 degrees) whose radius was worked out from the ideal angle rather than the stored vertices can read as clamped by up to 1.3e-6 of the coordinates. Tolerances 1e-7 and 3e-7 both pass the suite; 1e-6 hides 0.1 percent at 1e3 and 1 percent at 1e4, and 1e-5 hides 1 percent at 1e3.
- `fillet_corner` is the only place that decides, so the resolver warning (`core/resolve.py`) and the fillet modal's "Clamped at N of M corners" readout and clamped-arc colouring (`core/fillet_logic.arc_preview`) agree.

## C19 - Phase 7 and 8 design decisions (agreed with the owner on 2026-10-24)

These settle the open decisions listed under Phase 7 and Phase 8 in plan section 12. The rest of each phase's "Proposed shape" in the plan stands.

- **3D path type.** Phase 7 adds a separate 3D path object (non-planar wire mesh) next to the planar sketch. Planar sketches, their data model and every earlier decision stay unchanged. Extrude is not offered for 3D paths.
- **Profile up on a 3D path: surface normal.** At each path point the profile's up direction is the normal of the face the point was snapped to or placed on. Between points it blends between neighbouring normals. Mitres use the bisecting plane of the two segments with the C2/C12 mitre-limit rule.
- **No link to the source object.** Snapped and surface points are copied when drawn, together with the face normal at that point. The path is independent afterwards and does not follow the object if it moves or changes.
- **Free points on the surface.** While drawing, a point snaps when it is near a snap target (vertex, edge midpoint, nearest point on an edge); otherwise it lands on the surface under the cursor (ray cast against visible non-sketch objects). Points that hit no surface are not added.
- **Normals face the viewer (QA round 1, 2026-10-24, decided by the orchestrator on the owner's behalf; reversible).** The normal stored with a point is the face normal oriented towards the viewer at draw time: a surface hit whose normal points away from the cursor ray (dot with the ray direction > 0) is flipped, so drawing on the inside of a room or on the back of a single-sided plane puts the profile on the visible side. `ObjectBVH.ray_cast` does the flip. Later edits of the path or a changed view do not change a stored normal.
- **Normals of snapped points (QA round 2, 2026-10-24, replaces the round 1 wording).** A vertex, edge midpoint or point-on-edge snap lies on two or more faces. When the scene source is built, every snap vertex stores the world space normals of its adjacent polygons and every snap edge those of its 1 or 2 adjacent polygons, taken from the evaluated mesh (equal normals to 5 places listed once; an object over the snap cap has no snap points, so none of this). `snap_placement` picks from that exact set, with no distance search and no tolerance, so it does not depend on the object's distance from the origin or its scale. Only snaps without adjacency (a path vertex, a loose vertex) use `normals_at`, a search with a reach of 1e-6 relative to the point's coordinates (the larger of the local and the world ones, about 10 float32 ulp), nearest first, deduplicated by rounding, at most 64 normals; if that finds nothing the nearest surface normal is used. The pick among the candidates is, in order: (1) faces that face the eye and are visible come first, then the ones that merely face it (QA round 3: a face buried by an abutting object faces the eye but is not visible; a face is visible when a ray from the eye to a probe point just above it meets nothing before it; the probe is the snap point moved 5 percent of the way to a probe target inside the face and as far up along the normal, with the limits of QA round 4 below; only done when two or more faces face the eye, with the probes the scene recorded and within the probe and ray limits of QA rounds 5 and 6 below, which test the most frontal normals first and pick the probes of a normal by a canonical order, never by the order of the polygons; the result is kept with the point's candidates and used again by the re-pick), and when only back faces are left (the inside of a room) all of them stay and the pick is flipped towards the viewer (round 1); (2) with a previous path point, the faces of that set that contain it (`abs(n . (previous - p))` within 1e-4 of the distance plus 1e-6 of the coordinates) are preferred: exactly one is taken, several are narrowed to those, none leaves the set as it is (so a face the segment lies on but the viewer cannot see does not beat a face in view); if several are left, the points before the previous one (up to 4, nearest first) narrow them the same way, where a point that lies on none of the faces left is skipped and the next one is tried (QA round 3; before, the first such point ended the evidence); (3) the smallest angle to the eye, where faces within 3 degrees of the best are a tie settled by the closest match with the previous path point's normal; without a previous point the pick is the best eye angle (not "the first found"). Each snapped point with several faces keeps its candidate set and the eye direction of the moment. When a later point is placed, the run picks again, with the same function, every point of this run created by the run (never a path vertex that existed before, never a second visit to one of the run's own) that is within 2 places behind the new point and still has several candidate faces. The evidence is its neighbours in the order previous, next, 2 back, 2 ahead (at most 4), narrowing as above, with the point before it as the continuity tie-break. A point not yet written (the first, at the second click) just carries the new normal into its vertex; a written one gets a `SET_NORMAL` command, which `PathEditor` applies to the session's own vertex in the same edit-mesh update as the click, so Esc still removes them with the rest of the run and the run stays one undo step. Closing onto the first point adds no position and re-picks nothing. A rim loop on a cube therefore stores the top normal at all four corners from 10, 20, 35 and 60 degrees, whichever corner and direction it starts with and whichever side the eye is on (tested over 384 start, direction, azimuth and elevation combinations). Known limit: a point is only re-picked while it is within 2 places of the newest one, and the last point of a run keeps the pick made when it was placed. Very small objects (about 1e-4 units) may pick differently because of the absolute floors in the visibility and containment tolerances.
- **Path vertex reuse (QA round 3).** A snapped point within 1e-6 of a path vertex, relative to the larger of 1 and the point's distance from the origin (about 10 float32 ulp), is that vertex. It was 1e-4, which merged clicks 0.1 units apart at 1e3 and 3.7 units apart at 3.7e4.
- **Probes, safeguard and path vertex reuse (QA round 4, 2026-10-24).**
  - *Probe targets (W1).* The face centre lies outside a concave face (the floor of a U shaped pit), so the probe moved into solid and hid the floor. The scene now records, per (snap vertex or snap edge, adjacent face), a `Probe(target, size)`. For a vertex the target is the centroid of the face's loop triangle at the vertex with the largest angle there; for an edge the centroid of the loop triangle that has the edge (a triangle lies inside the face, so the target does too). The operator reads the loop triangles of the evaluated mesh; plain test data is triangulated with `tessellate_polygon`. `size` is the shortest edge of the face at the snap (the two edges at a vertex, the edge itself). `SceneSource.vertex_probes`, `edge_probes` and `snap_probes` replace the `*_centres` lists.
  - *Probe step (O1).* The step is the smallest of 5 percent of the distance to the target (`PROBE_FACE`), 1 percent of the distance to the eye (`PROBE_SIGHT`; in an orthographic view that distance is the size of the scene), 10 percent of `size` (`PROBE_EDGE`, both projections) and what lands the probe point 10 pixels from the snap point on screen (`PROBE_PIXELS`, measured with `view.project`). The edge share alone does not help on a face with long edges (a tenth of a 40 unit block is 4 units, and the scene sized sight distance gave 0.7), the pixel limit is what keeps the probe of a big face next to the point in an orthographic view. In a perspective view 10 pixels is about 1.2 percent of the distance to the eye at 800 pixel focal length, so there it changes little. Measured with the reviewer's random scenes (3000 trials, cubes touching, thin, apart and big): wrong "visible" 16 (perspective) and 16 (orthographic), wrong "hidden" 4 and 5, the same as the earlier probe within 1 case.
  - *Safeguard.* When the visibility test removed exactly one face that faces the eye, and that face is the only one through the point that contains the previous path point, it stays in the pool: the path is evidence that the viewer saw the face. A previous point on the edge shared by two faces is no evidence (both contain it), so a face buried by an abutting object is still dropped along a segment on their shared edge.
  - *Reuse (W2).* A visible path vertex within 0.5 pixels (`OWN_PIXELS`) of the chosen scene vertex on screen is taken instead of it, whatever the float error of the round trip through the path's local space (a path vertex at 1e4 comes back about 1e-3 off). The reuse distance of C19 round 3 becomes 1e-6 times the larger of 1, the point's distance from the origin and the path object's offset from the origin (`reuse_scale`, `PathEditor.offset`), because the local coordinates are as large as that offset.
- **Probe and snap refinements (QA round 5, 2026-10-25).**
  - *Degenerate loop triangles (W1).* A face with a vertex on one of its edges can get a zero-area loop triangle from Blender; the largest-angle rule then picked its 180 degree corner, whose centroid is on the face boundary, and the target could equal the snap point (reach 0, counted visible untested, so a face buried by a flush box stayed in `front`). `face_probes` now ignores triangles with area below `DEGENERATE_AREA` (1e-6) times the longest side squared plus `DEGENERATE_COORD` (2e-7) times the longest side and the largest coordinate (the float32 error of the corners) when it chooses the corner target and the edge owner. A corner or side left without a triangle takes the centroid of the face's nearest other triangle, a face with none its vertex mean. The `tessellate_polygon` and fan fallback go through the same function, so the rule applies there too.
  - *Coplanar faces (W2).* `vertex_probes` and `edge_probes` hold, per listed normal, a tuple of the `Probe` of every face that contributed it (they kept only the first face's, so a flat patch's visibility depended on polygon order). `front_faces` counts a normal visible when any of its probes is: they are tried in turn, at most `MAX_PROBES_PER_NORMAL` (4) per normal and `MAX_PROBE_RAYS` (16) rays in all (it was 8 faces); a probe with no extent is skipped, a normal with none to test counts as visible, and once the ray budget is spent the rest count as visible.
  - *Own vertex beside a scene vertex (W3).* The 0.5 pixel capture of the reuse rule also needs the path vertex within `max(1e-3, 1e-4 * max(|co|, path offset))` of the scene vertex in the world (`OWN_DISTANCE`, `OWN_MIN_DISTANCE`; `_own_beside` gets `reuse_scale`). A vertex far behind the scene vertex on the same sight line (a silhouette alignment) no longer captures the click. 1e-4 of the offset still covers the round trip at 1e4 (about 1e-3). At unit scale the capture distance is therefore 1e-3, no longer the 3 to 4 thousandths of round 4.
  - *Sight tolerance far from the origin.* `is_visible` allows `1e-4 * max(1, distance)` plus `SIGHT_COORD_TOLERANCE` (1e-6) times `max(1, |co|)`: the ray and the point are float32, so a close-up (eye 0.1 to 1 unit away) at 1e3 to 1e4 from the origin called visible faces hidden (up to 9 percent of the cases, 0 after).

- **Probe order and ray budget (QA round 6, 2026-10-25).** The limits of round 5 depended on polygon order once they bit. (1) The facing normals are taken most frontal first (largest `dot(normal, to_eye)`, ties by the normal's coordinates), so the `MAX_PROBE_RAYS` (16) budget goes to the normals the pick would choose; `front_faces` returns them in that order. (2) The probes of one normal that are testable (some extent, target away from the snap point) are sorted by the distance of the target from the snap point, then by its coordinates and size, and when there are more than `MAX_PROBES_PER_NORMAL` (4) a spread across that order is tested: the nearest, the farthest and evenly spaced ones between (`_probes_to_test`). The result no longer changes with the order of the faces. Known limit: with more than 4 coplanar faces at a vertex and almost all of them buried, a visible one that is neither the nearest nor on the spread is not found (the normal counts as hidden, the same for every order); once the 16 rays are spent the remaining normals count as visible.

- **Ctrl in the 3D draw tool.** Snapping is on by default in 3D, so Ctrl held means no snapping: the point is placed on the surface under the cursor, without the Shift angle lock. Shift (angle lock) turns snapping off too, as before. The header said "Ctrl no snapping" (C24 replaces it: the 3D header now says "hold Shift or Ctrl" in every shape). Ctrl with a key press (C, Enter and so on) is still swallowed, as in C15. The Sketch tool description and the tool settings line say Ctrl snaps to points for planar sketches and turns snapping off for 3D paths. Ctrl and Shift held together keep the Shift angle lock and skip snapping.
- **Reversing normals in the 3D sweep (QA round 2).** Where neighbouring stations' up directions (the normals projected off the tangent) differ by more than 120 degrees the profile twists through a half turn or more, as when a single-sided plane is drawn on from both sides. The sweep is not changed (the profile stays on the side the viewer saw) and warns "Surface normals reverse N times along the path; the profile twists there" ("once" for 1), N counted in pairs of neighbouring stations (closed paths include the closing pair).
- **Snap sources and segments.** Sketch outputs (`.out`), other sketches, the path itself, hidden objects and meshes without faces are not snap or hit targets. A segment between two points is a straight chord: across a convex edge or a curved surface it cuts through the solid, and the sweep follows the chord, not the surface.
- **Arcs are baked into segments.** Arcs drawn in Phase 8 become a fixed number of straight segments at draw time, like circles today, so Trim, Extend, Subdivide and the resolver need no arc support.
- **Defaults until the owner says otherwise.** Trim, Extend, Fillet and Subdivide are not required to work on 3D paths in Phase 7. Rectangle, circle and arc get no extra options (centre-drawn, rounded corners, rotation) in Phase 8 beyond what the draw tool already does, and all three work on 3D paths as well as planar sketches.

## C20 - Phase 7 module contract (agreed 2026-10-24)

- **Object model.** A 3D path is a mesh object with `sketch_tools.is_sketch = True` and a new `sketch_tools.is_path_3d = True` (the one data-model addition, per C19). Its vertices keep full 3D positions in object local space; `sketch.new_path_3d` creates it at the world origin with an identity matrix. Per-vertex attribute `st_normal` (FLOAT_VECTOR, POINT domain, object local space, unit length) holds the surface normal captured when the point was drawn. `st_fillet_radius` and `st_fillet_id` exist but are ignored on 3D paths in Phase 7.
- **`core/resolve3d.py`.** `PATH_NORMAL_ATTR = "st_normal"`; `@dataclass Chain3D(points: list[Vector], normals: list[Vector], closed: bool)`; `@dataclass ResolvedPath(chains: list[Chain3D], warnings: list[str])`; `resolve_path_bmesh(bm) -> ResolvedPath` never modifies `bm`. Chain walking, junction splitting, closed-loop rules and the cross-chain weld follow plan 4 and C8/C9 in 3D; no fillets, no nesting, no winding normalisation.
- **`builders/sweep3d.py`.** `build_sweep_3d(resolved_path, rings, mitre_limit, smooth, cap_ends) -> (bm, warnings)`, bm in object local space, caller frees it. Rings are the existing profile rings (`.points`, `.closed`, `.depth`, `.parent`). For a planar path whose normals all equal the plane normal it must reproduce `builders/sweep.build_sweep` exactly.
- **`ops/draw3d.py`.** `SKETCH_OT_draw_3d` (`bl_idname = "sketch.draw_3d"`), module-level `classes` and `close_all()`. Started from the existing Sketch tool's LMB keymap through an extra keymap item; `sketch.draw` refuses 3D paths and `sketch.draw_3d` accepts only 3D paths, so one tool serves both.
- **Other tools.** `sketch.draw` (2D), `sketch.fillet`, `sketch.trim`, `sketch.extend`, `sketch.subdivide` and `sketch.set_plane_from_face` refuse 3D paths in Phase 7 (C19 default). Extrude on a 3D path produces no output and the warning "Extrude needs a planar sketch".

## C21 - Phase 8 shape options: contract and decisions (agreed 2026-10-25)

- **Shapes.** Polyline, rectangle (two opposite corners), circle (centre, then radius), three-point arc (start, a point on the arc, end) and centre arc (centre, start, end; the arc runs counter-clockwise from start to end as seen against the plane normal, and the angle is never zero). All are baked into straight segments at draw time (C19). Rectangle and circle keep their Phase 3 behaviour; no extra options.
- **Segment counts.** Circles use the `circle_segments` preference as today. An arc uses `max(2, ceil(circle_segments * angle / (2 * pi)))` segments, so it matches a circle's density.
- **Choosing a shape.** A WindowManager enum `sketch_tools_shape` (POLYLINE, RECTANGLE, CIRCLE, ARC_3PT, ARC_CENTER), shown in the Sketch tool's header, sets the shape the next run starts with. Inside a run, the existing keys R, O and P switch shape while fewer than two points exist, and a new key A cycles three-point arc and centre arc; the tool keymap gets no new idle key, so Blender's A (select all) still works while no run is active. R and O idle keymap items stay as in C15. The same picker (an expanded icon row with a short hint line) also appears in the Sketch panel in edit mode, for planar sketches and 3D paths, so it can be found outside the tool header; it edits the same enum.
- **`core/shapes.py` (pure, no bpy).** `rectangle_points(a, b)`, `circle_points(centre, radius, segments)`, `arc_three_points(p0, p1, p2, circle_segments)` and `arc_centre(centre, start, end, circle_segments)`, all on 2D tuples, returning point lists (`arc_*` return the points from start to end inclusive, or None for collinear or degenerate input). The 3D tool maps its plane to 2D and back.
- **3D paths.** A shape on a 3D path lies in the plane of the face under its first point: the plane through that point with its stored (viewer-facing) normal. The plane's x axis is the view right vector projected onto the plane. Every generated point takes that first point's normal. Clicks after the first are taken as the cursor ray's intersection with that plane, so a shape never bends over other faces. A three-point arc instead lies in the plane through its three placed points, and its generated points take the first point's normal. Typed values stay unavailable in 3D (C19).
- **One undo step per shape; Esc cancels it** (C15). Closed shapes (rectangle, circle) produce closed chains; arcs produce open chains.
- **3D implementation notes (Phase 8 part B, 2026-10-25).**
  - *Run.* `PathSession(shape, circle_segments)`; the operator reads `sketch_tools_shape` at invoke (a missing or unknown value is a polyline) and the `circle_segments` preference. A run is click, click(, click): rectangle and circle take two clicks, both arcs three. Nothing is written before the completing click, which writes the whole shape in one edit-mesh update and ends the run, so the operator's undo step holds exactly the shape. There is no drag-to-size in 3D, as before. Keys R, O, P switch while at most one point exists, A goes from any shape to the three-point arc and between the two arcs; RMB and Enter cancel a shape that is not complete (a polyline of two points or more is kept); C only closes a polyline. Shift (angle lock) exists for polylines only; for shapes Shift and Ctrl both turn snapping off.
  - *Plane.* The plane of rectangle, circle and centre arc is fixed by the first click (position and stored normal). Its x axis is the view's right vector at that click, projected onto the plane (`PathProjector.right`, `snap3d.plane_basis`; world X, then world Y, when the projection has no length), so orbiting the view mid-shape does not turn the shape. Clicks after the first are the cursor ray's intersection with the plane (`snap3d.place_on_plane`); a ray within 0.001 (cosine) of parallel, or whose intersection lies behind the eye, places nothing and the header says so. A snap target in reach is moved onto the plane along its normal; the placement never carries a path vertex to reuse. All new vertices carry the first point's normal.
  - *Reuse.* The first point, when it is an existing path vertex, is the rectangle's first corner (the nearest corner to it) and the start of a three-point arc; a three-point arc's end click on a path vertex is that vertex too. A circle's or centre arc's first point is the centre, which is not a vertex.
  - *Three-point arc normal.* Its first point's normal is picked again when the arc is complete, with the other two points as evidence, exactly as the re-pick of a polyline does (only if the run created that vertex and it touches several faces). Without it a rim arc started at a cube corner kept the front face the eye preferred and its sweep twisted. The other shapes keep the normal the first click had ("placed as today"): a rectangle or circle whose first click is a cube corner lies in the plane of the face the eye prefers.
  - *Known limit.* A normal fixed for the whole shape that lies in the plane of an arc (an arc across faces whose first normal is parallel to the plane of the arc) reverses the profile's up direction once along the sweep, and the sweep warns "Surface normals reverse once" (C19).

- **Planar draw tool details (Phase 8 part A, 2026-10-25).**
  - *Header and start.* `props.SHAPE_ITEMS` defines the enum (with icons) and `props.register` adds `WindowManager.sketch_tools_shape` (removed again in `unregister`). The tool header shows it as icon-only expanded buttons plus the hint text. The tool's LMB item passes `mode='SETTING'` (`props.FROM_HEADER`), an extra value of `sketch.draw`'s `mode` property that `invoke` resolves to the header shape; R and O still name RECTANGLE and CIRCLE, and a programmatic call with an explicit mode ignores the header. The operator's `mode` enum now lists the five shapes plus `SETTING`.
  - *Keys.* A is handled inside the run only (no idle keymap item). While fewer than two points exist it alternates ARC_3PT and ARC_CENTER, and from any other shape it starts with ARC_3PT. R, O and P also leave an arc under the same rule. The first point survives a switch.
  - *Three-point arc.* Click the start, a point on the arc, the end. Nothing is written before the third click. Cursor-driven only: typed values, Tab and Backspace are ignored (the header says "no typed values for this arc"). Ctrl takes the nearest vertex (start and end reuse it; the middle point only uses its position) else the grid; Shift locks the chord from the start to the end point to multiples of 45 degrees from sketch X (length kept, rounded to the grid under Ctrl); a click that would be collinear or coincident does nothing. The preview is a straight line after the first click and the arc through the middle point to the cursor after the second, with a Radius readout.
  - *Centre arc.* Click the centre (never a vertex), click the start (sets the radius, towards the cursor), click the end (only its direction counts; it is projected onto the circle). Typed Radius (scene base unit, negative uses the magnitude) for the second click and typed Angle in degrees for the third; Enter or a click commits either. A typed angle is counter-clockwise from the start and wraps modulo 360, so -90 gives the 270 degree arc, and 0 or a multiple of 360 is not committed (an arc is never zero). Shift locks the start direction to 45 degree steps from sketch X and the sweep to 45 degree steps from the start; Ctrl rounds the radius to the grid (second click) and turns the cursor into the nearest vertex or grid point (third click, direction only; the end reuses a snapped vertex only when it lies on the circle within 1e-6 of the radius). The preview shows the arc, both radius lines, an Angle and a Radius readout.
  - *Ending.* Esc cancels at every stage. RMB, N and Enter with nothing typed cancel an arc too (like a rectangle or circle without its second point), C does nothing. Arcs have no click-drag commit (a drag has no clear second and third point). The result is an open chain; new vertices are sharp (radius 0, id 0); one undo step per shape (checked live in a GUI Blender 5.1.1: one undo removes one arc).
  - *Rectangle order.* `shapes.rectangle_points` is always counter-clockwise; the planar tool swaps its corners 1 and 3 when the cursor lies on the other side so the vertex order stays what Phase 3 produced (the resolver normalises winding anyway).
  - *Arc segment count* uses `ceil(circle_segments * angle / (2 * pi) - 1e-9)`: the slack stops float noise turning a quarter circle at 32 segments into 9 segments. It only covers the planar double-precision case: in 3D, float32 coordinates mean an arc whose sweep is an exact multiple of `2*pi/circle_segments` can get one extra segment. `shapes.circumcircle` is public because the three-point preview reads its radius.

## C22 - Phase 5 extras chosen by the owner (2026-10-25)

The owner picked two of the Phase 5 items: scene snapping for flat sketches, and a boolean union sweep option. (C23 supersedes the "Ctrl snapping" of the planar tool: snapping now follows the snap magnet and Ctrl flips it.) Live preview in edit mode and the JSON profile library stay unbuilt. Three-point arcs were delivered in Phase 8 and scene snapping for 3D paths in Phase 7.

- **Scene snapping for flat sketches.** In the planar draw tool, Ctrl snapping also considers other visible mesh objects: their vertices, edge midpoints and nearest points on edges, within `snap_pixel_threshold`, visible from the eye only (occlusion test as in Phase 7). The same object exclusions as Phase 7 apply (no sketches, no sketch outputs, not the sketch itself, no meshes without faces, the Phase 7 point caps). Priority: the sketch's own vertices first (they are reused, as today), then scene vertex, midpoint, edge point, then the grid. A scene snap is projected orthogonally onto the sketch plane and becomes a new sharp vertex. Reuse `core/snap3d.py` (SceneSource, find_snap or its parts) rather than duplicating it. Applies to every planar shape click that already honours Ctrl (polyline, rectangle corners, circle, both arcs as C21 defines). *Built (part A, 2026-10-25).* `DrawController` takes `scene` (a `snap3d.SceneSource`) and `scene_view_factory` (`draw3d.projector_factory`, the Phase 7 `PathProjector`); `SKETCH_OT_draw.invoke` builds the source once with `draw3d.build_scene_source(bpy.context, obj, normals=False)` (the new `normals` flag skips the face normals and probes only the 3D tool reads; same exclusions, caps and notice, and the notice is shown in the header) and the controller owns it: `close()` clears it, so finish, Esc, error, cancel, `close_all`, a lost view, leaving edit mode and a failed start all drop it. A build failure prints, reports a WARNING and leaves scene snapping off for that run, drawing still works. The press that is passed through (over an overlay) builds nothing. Per pointer event with Ctrl: the sketch's own vertices first (`nearest_snap`, as before, no occlusion test), and only when none is in reach and Shift is not held `snap3d.find_snap(scene, view, mouse, snap_pixel_threshold)` (vertex, then midpoint, then edge point, nearest on screen within a kind, occluded ones skipped). **Shift disables scene snapping** (as it does in 3D), so Shift+Ctrl keeps the Phase 3 rule (locked direction, length rounded to the grid) and still reuses a sketch vertex in reach. The scene point is mapped into sketch local space with the inverse of `matrix_world` and its z is dropped (an orthogonal projection onto the plane; the sketch is at unit scale, C15), giving `draw_logic.Snap(ref=None, xy, kind)`; `ref` None makes the session treat it as a free point, so it becomes a new sharp vertex (radius 0, id 0) and `_place_first` allocates a session ref for it. Every other rule already took `Snap.xy` and `Snap.ref` (rectangle corner, circle centre and radius point, three-point arc points, centre arc start; the centre arc's end click only uses the direction, and reuses a vertex only when it lies on the circle, which a scene snap never does). A scene point whose projection coincides with an existing sketch point creates a coincident vertex (the resolver welds them, C9) and does not close a chain by itself; Ctrl on the sketch's own first vertex still closes. The overlay marks the projected point with the snap square and puts a label above the readout lines (`Scene vertex`, `Scene edge midpoint`, `Scene point on edge`; none for a sketch vertex).
- **Boolean union sweep option.** New property `sw_union: BoolProperty(default=False)` on `SketchToolsProps` (an addition to the plan 3.1 data model, recorded here). When on, after the sweep is built for a planar sketch or a 3D path, overlapping and self-intersecting parts of the swept solid are merged into one closed mesh with Blender's exact boolean (self intersection on). It runs in `core/build.py` through `bpy.data` only (a temporary hidden object and modifier evaluated through the depsgraph, then removed), never `bpy.ops`, so no undo steps are pushed and the output stays a plain mesh without modifiers. If the swept result is not a closed solid (open profile strips) or the boolean fails, the un-merged result is kept and the panel warns. Smooth and sharp flags are re-applied where possible and the limitation documented if not.
- **Sweep union, as built (part B, 2026-10-25).**
  - *Modifier configuration found to work in 5.1.1.* A Boolean modifier with `operation='UNION'`, `solver='EXACT'`, `operand_type='COLLECTION'`, `collection=<an empty Collection datablock that is in no scene>`, `use_self=True`, on an object holding the sweep. Checked on two cubes in one mesh and on figure-eight sweeps: the pieces merge into one closed shell with the right volume (two 2x2x2 cubes offset (1, 0.5, 0.3): 13.45 = 16 - 2.55). `operand_type='OBJECT'` with no object does nothing (the mesh comes back unchanged), so it cannot be used for a self union. A collection operand also merged with `use_self=False` and with no collection at all, so the flag may not matter in 5.1; it stays on because it is the documented self-intersection switch and the empty collection because it is the form that cannot be read as "disabled" by older versions (4.2 not tested). `use_hole_tolerant` made no difference on the test meshes and is left off. `bmesh.ops` has no boolean in 5.1 (no `intersect` or `intersect_boolean` in `bmesh.ops`), so the modifier is the only route.
  - *No bpy.ops, no visible scene.* The object, its mesh, the empty collection and a throwaway Scene are made through `bpy.data`; the object is linked into that scene's master collection and the depsgraph is taken under `bpy.context.temp_override(scene=<throwaway>, view_layer=<its first>)` + `evaluated_depsgraph_get()`. The user's scene, selection, active object and undo stack are not touched, and the main depsgraph is not invalidated (linking a temporary object into the user's scene would force a relations rebuild twice per rebuild). A depsgraph of a scene that is not active does not call the `depsgraph_update_post` handlers, and the temporary object is no sketch anyway (checked in a GUI Blender 5.1.1 launched with `--factory-startup`). Tested headless by `test_union_evaluation_triggers_no_depsgraph_update_handlers`: a counting `depsgraph_update_post` handler (proved alive first) sees nothing inside the evaluation window of `_boolean_once`; evaluating in the user's scene instead makes it fail (the handler then sees the temporary object, mesh and collection), which the earlier handler test could not (it returned early on `is_rebuilding()`). All four datablocks (scene, object, collection, mesh) are removed in a `finally`, each removal on its own so one failure cannot leave the rest. Tests name them with `build.UNION_TEMP_NAME` and check that none survive rebuilds, errors and unregister.
  - *Where.* `core/build.py` only: `_build_sweep` calls `_union_sweep(bm, sw_smooth)` after the builder (planar and 3D alike) when `sw_union` is on. `builders/` is untouched and pure. `bpy.context` is used in that one place (the override). Extrude ignores the option.
  - *Gates, in order.* (1) No faces: nothing to do, no warning. (2) Not a closed solid (any edge without exactly two faces walking it in opposite directions, or a loose vertex: an open custom profile ring, `sw_cap_ends` off on an open chain): the un-merged sweep stays and the warning is "Union skipped: the sweep is not a closed solid". (3) No two faces that share no vertex intersect (`BVHTree.overlap` over the faces): the sweep is already its own union, so the boolean is not run and the output keeps its ngons; no warning. `BVHTree.overlap` is not a box test: after the box overlap it runs an exact triangle-triangle test on each candidate pair (checked in 5.1.1: faces of a tight ring, of a U of two close diagonal arms and of parallel diagonal triangles have overlapping boxes and are not reported; transversal crossings are; probed in 5.1.1, it does not report box-overlapping pairs that do not intersect, edge-edge contact, vertex-vertex contact, a vertex on another triangle's edge, an edge touching an edge's interior, or coplanar overlapping or identical triangles, so that contact is skipped here, silently; it does report transversal crossings (even 1e-6 deep), a vertex lying in another triangle's interior and an edge lying in another triangle's interior, so contact on a face interior (flush faces, a vertex or edge lying on a face) passes the gate even with no volume overlap, and the solver may return the mesh unchanged for it, which is shown as "Union failed" (see Result). No separate triangle test is needed; `mathutils.geometry` has no 3D `intersect_tri_tri` in 5.1 anyway). Measured cost of the gate: 0.4 ms (194 faces), 1.3 ms (770), 7.6 ms (4800 faces, crossing), 5.8 ms (6400 faces, no contact). (4) The boolean.
  - *Retries and validation.* Round bars crossing at equal height meet in ridges the exact solver can leave a hole at (a figure-eight CYLINDER sweep came back with 3 boundary edges). The input is moved by a few thousandths of its size (`_UNION_RETRY_SHIFTS`, up to three attempts: unshifted, then two shifts), which rounds every coordinate differently and breaks the tie; the result is moved back, and the vertices the solver kept are put back to their exact original coordinates. A result is accepted when it has faces, is a closed solid by the same test, and its volume is above 0 and no more than the un-merged sweep's volume (the sum over overlapping parts) plus 0.01 percent. A result that is unchanged from the input (same vertex and face counts and the same volume within one millionth) is rejected too: a real union adds seam vertices and loses the shared volume, so an identical mesh means the solver did nothing, either because it was not run properly (for example an older Blender not honouring `temp_override(scene=...)` in `evaluated_depsgraph_get()`) or because the gate saw only flush contact with no volume overlap; unrejected, it would pass as a closed solid of the summed volume (`_is_unchanged`). A no-op counts as a failed attempt and is retried like any other, then reported. If no attempt is accepted, or the evaluation raises, the un-merged sweep stays and the warning is "Union failed; showing the un-merged sweep"; an exception is printed once per distinct message (`build.clear_error_log` resets it).
  - *Shading.* The boolean keeps the sharp flag of old edges but returns some of the faces it splits flat shaded and its new seam edges smooth. With `sw_smooth` on, every face of the result is made smooth and every edge folding by more than 30 degrees (the C5 angle) is made sharp; sharp edges are never made smooth. End caps stay flat-looking because the builder already marked their boundary edges sharp and the boolean keeps those (tested). Not preserved: the exact set of the builder's sharp edges is replaced by the dihedral rule on the merged mesh (a smooth low-resolution profile whose corners turn more than 30 degrees is sharp in both), and the per-face smooth flag of the caps (they are smooth-flagged with sharp borders, the same shading). With `sw_smooth` off nothing is touched; the faces come back flat. There are no other attributes or materials on a sweep to carry.
  - *Result.* A plain mesh without modifiers in the output object. Hollow profiles (TUBE) keep their cavities as extra closed shells, so "one shell" holds for solid profiles. Disjoint chains stay separate shells. Touching-only contact is split by what the gate reports. Edge-edge and vertex-vertex contact is not reported and is skipped silently, as is coplanar-only overlap. Contact on a face interior (flush faces, a vertex or edge lying on a face) is reported by the gate, and the solver may return the mesh unchanged; that is rejected as a no-op and shown as "Union failed; showing the un-merged sweep" after three attempts, with the un-merged sweep kept. Example, the "flush T": a SQUARE 0.2 bar along x from -1 to 1 and a stem from (0.3, 1.0) to (0.3, 0.1) (16 vertices and 12 faces in and out, same volume). Before the unchanged check this was accepted silently; pinned by `test_flush_face_contact_is_reported_by_the_gate_and_shown_as_union_failed`.
  - *Measured (Blender 5.1.1, headless, this machine).* Typical sweeps: 36 to 400 faces 0.01 to 0.1 s; figure-eight CYLINDER 48 segments about 0.1 to 0.2 s; trefoil/rose CYLINDER (1000 to 1400 faces) 0.14 to 0.3 s; TUBE rose (1900 faces) 0.6 s. A failed union costs up to three attempts. Because the option is evaluated on every rebuild, dragging a profile slider with the option on costs that per tick; with it off the cost is zero. Random scribbles with sharp mitred corners are the hard case: SQUARE and HALF_ROUND failed in 1 of 25, CYLINDER 0 of 25, TUBE 16 of 25 (identical results on every retry, so a structural problem of mitre-folded hollow tubes rather than a tie); they fall back to the un-merged sweep with the warning.

## C23 - Snap toggle for planar drawing (2026-11-02, extends C15 and C22)

The flat Sketch draw tool follows Blender's own snap toggle (`scene.tool_settings.use_snap`, the magnet icon, Shift+Tab), as snapping works elsewhere in Blender.

- **Rule.** Snapping is active when `use_snap != event.ctrl`. Magnet off (the default): exactly the C15 and C22 behaviour, Ctrl held snaps and releasing it draws freely. Magnet on: snapping is active without Ctrl and holding Ctrl turns it off for that moment.
- **What follows the flag.** Everything Ctrl drove in the planar path: reusing a sketch vertex, scene snapping (C22), grid snapping of free points, and the grid rounding of rectangle, circle and arc sizes. `DrawController._pointer` computes the flag once (`effective_snap`) and passes it as `Mods.ctrl`, so `core/draw_logic.py` is unchanged and stays bpy-free. The raw `event.ctrl` is kept where it means a keyboard modifier (Ctrl+key shortcuts are still not read as keys). Shift behaves as before (it still disables scene snapping and locks the angle). With the magnet on, plain Shift therefore gives a locked angle with the length rounded to the grid, which was Shift+Ctrl before; with the magnet off, Shift+Ctrl still does.
- **Read live.** The toggle is read on every event through a `snap_toggle` callable given to `DrawController` (None means off, which keeps existing callers and tests unchanged), so flipping the magnet during a run takes effect on the next event. The operator's reader is `draw_tool.magnet_on(bpy.context)`, which reads a missing scene or tool settings as off instead of aborting the run.
- **Shift+Tab.** The modal used to swallow it as Tab (next typed field). Shift+Tab now returns PASS_THROUGH so Blender's own keymap flips the magnet; plain Tab is still the next-field key.
- **Out of scope.** The 3D paths (`ops/draw3d.py`) already snap by default with Shift or Ctrl turning it off (C19), unchanged. The Fillet modal's Ctrl radius rounding is unchanged.
- **Wording.** Ctrl flips snapping only while it is held, so the planar header hint and the tool settings line say "hold Ctrl to flip snapping" and the tool description says "Snapping follows the snap magnet (Shift+Tab); hold Ctrl to flip it while held". The 3D header wording changed in C24 ("hold Shift or Ctrl to turn snapping off").
- **Header state.** The planar header starts with the effective state, "Snapping on" or "Snapping off", then any hint (the view is edge-on to the sketch or the sketch is behind the view), then the scene snap notice, then the instructions: `Snapping off | <hint> | <notice> | <instructions>`. The controller (`ops/draw_tool.py`) keeps the Ctrl state of the latest event and refreshes the header on every event, so pressing or releasing Ctrl shows at once and a magnet flip shows on the next event. The press that starts a run sets that Ctrl state before its first header is built, so a run started with Ctrl held shows the right state at once.
- **Header length.** Blender clips an overflowing header at both ends, so putting the state first is not enough: the whole line must fit. Measured at the default layout, a 1574 px wide 3D area at about 5.15 px per character fits about 305 characters. Before this fix the centre arc after its first click was 338 characters (the state was clipped), the three-point arc with one point 305, the polyline 296, and either the notice (about 90 characters) or the hint (about 80) in front pushed every mode over. The bound is 260 characters without a notice or hint (leaves room for a smaller viewport) and 300 with a notice and a hint both on the line, pinned for every shape, point count and typed or untyped state by `test_the_header_stays_within_the_width_that_fits_with_the_state_first`. Longest now: polyline 217, rectangle 215, centre arc 205, circle 200, three-point arc 198; 296 at most with both a notice and a hint. How it was done: the notice is "Snap limit: N object(s) not snapped" in the planar tool, where a capped object gives no snap points at all (its BVH still occludes), and "Snap limit: N object(s) surface only" in the 3D tool, which still places on the surface (`build_scene_source` picks the wording from its `normals` flag), the hints are "View is edge-on, rotate it" and "Sketch is behind you, turn the view", the shape-switch tail is "R rect, O circle, P poly, A arc", the arc help lost its parentheticals ("again for the other arc", the centre arc's radius and angle explanation moved into one typing instruction), and "Esc cancels, Ctrl+Z off" replaces the longer back-out text. It is the same phrase in the 3D header (which got 15 characters shorter than "Esc cancels, undo is off while drawing"), and it says what is true: Ctrl+Z is off during a run, Esc drops the whole run, and a finished run is one undo step (C15), so it does not read as "this cannot be undone". The 0-point planar header now also says "click to place the first point, hold Ctrl to flip snapping", because the first point snaps too, and the header test requires "hold Ctrl to flip snapping" for every shape and point count. The 300 bound still holds with the longer Esc text and the new hint: 298 at most with both a notice (three digit count) and a hint on the line; 220 at most without; 192 at most for the 0-point header. The 3D header got the same treatment in C24. Every instruction needed for the current step stays, including "hold Ctrl to flip snapping".

## C24 - 3D path header (2026-11-02, extends C19 and C23)

The 3D path tool's header got the C23 treatment: the effective snapping state first, and a bounded length.

- **State rule (unchanged behaviour).** The 3D tool snaps by default and Shift or Ctrl turns snapping off for that point (`snapping=not (event.shift or event.ctrl)` for the plane shapes; `place(shift=..., ctrl=...)` for the polyline and the three-point arc). It does not follow the snap magnet; C23 does not apply to it. The header shows "Snapping on" when neither is held and "Snapping off" when either or both are.
- **Order.** `Snapping on|off | <hint> | <notice> | <instructions>`, built by `PathController._update_header` in `ops/draw3d.py`. `PathSession.header_text()` (`core/snap3d.py`) returns only the instructions (the degenerate-arc note is the first part of them). The hint is one of the three cursor hints, the notice is "Snap limit: N object(s) surface only".
- **Refresh.** The controller keeps Shift/Ctrl of the latest event (`_snap_off`, set in `handle()` before anything else, and in `start()` before the first header is built), so pressing or releasing either key shows the new state at once, also with the pointer outside the region or on any other pass-through event (the update runs before the pass-through checks; `test_a_modifier_pressed_outside_the_region_flips_the_3d_header_at_once`; the planar tool got the same guard for `_ctrl`, its modifier path already refreshed through `_leave`), and a run started with a modifier held shows the right state on its first header (compare the planar `_ctrl` fix).
- **Bounds.** At most 260 characters plain and at most 300 with the worst-case notice (three-digit count, 38 characters) and the longest hint, pinned over every shape, point count (0 to 6) and degenerate-arc note, with the state off (the longer form), by `test_the_3d_header_stays_within_the_width_that_fits_with_the_state_first`. There is no typed state in 3D (nothing can be typed). Longest header per shape, plain / worst case, before (no state) and after (with state):

  | Shape | Before | After |
  |---|---|---|
  | Polyline | 295 / 407 | 206 / 294 |
  | Rectangle | 230 / 342 | 209 / 297 |
  | Circle | 218 / 330 | 197 / 285 |
  | Three-point arc | 267 / 379 | 191 / 279 |
  | Centre arc | 275 / 387 | 197 / 285 |

  The old worst case used the old 69 character "The cursor ray does not meet the plane of the shape, no point placed"; the hint is now "Cursor misses the plane of the shape" (36), and the longest hint is "No surface under the cursor, no point placed" (44, also the text of the start warning). The rectangle has the least room left (297 of 300). The centre arc freed room when "(counter-clockwise)" became "(CCW)", which paid for "A other arc" in the arc shapes. Planar worst cases with both a notice and a hint: polyline 299, rectangle 297, centre arc 293, three-point arc 286, circle 282.
- **Final strings.**
  - Help: "3D path: LMB places a point on a surface or snap point"; "3D rectangle: LMB sets the opposite corner in the plane of the first point"; "3D circle: LMB sets the radius in the plane of the first point"; "3D arc: LMB places the middle point, then the end"; "3D centre arc: LMB sets the start, then the end (CCW)".
  - Polyline with two points or more: "RMB/Enter end, C close". With one point or none: "R rect, O circle, P poly, A arc", and in the two arc shapes "R rect, O circle, P poly, A other arc" so the A key switch is discoverable (the planar header says the same).
  - Snapping: polyline "hold Shift or Ctrl: snapping off, Shift locks 45 degrees" (Shift locks only once a first point exists), other shapes "hold Shift or Ctrl to turn snapping off". Then "no typed values", then "Esc cancels, Ctrl+Z off" (same as the planar tool).
  - The snap targets (vertex, edge middle, on edge) are no longer listed in the polyline help; they show in the overlay label next to the cursor.
  - Tool description (3D part): "Shift or Ctrl turn snapping off (Shift also locks the angle in a polyline)"; the 3D line of the tool settings says the same. Pinned by `test_the_tool_description_says_what_ctrl_does_for_planar_and_3d_paths`.
  - The planar header tail is "R rect, O circle, P poly, A other arc" in the two arc shapes too (`DrawSession.header_text`).
